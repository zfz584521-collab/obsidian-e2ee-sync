# 同步逻辑说明

本文档说明 Obsidian 同步插件的核心同步机制、增量规则和冲突处理策略。

---

## 一、同步模式：增量同步

本插件**不是全量同步**，而是基于变更日志的**增量同步**。

每次点击「立即同步」，插件执行以下 5 个阶段：

```
1. 扫描本地文件    →  对比本地基线索引，检测新增/修改/删除的文件
2. 读取远端日志    →  拉取其他设备上传的变更日志（仅拉取未处理过的新日志）
3. 应用远端变更    →  把其他设备的变更下载并应用到本地
4. 上传本地变更    →  把本地新增/修改/删除的文件加密上传到 S3
5. 追赶拉取        →  上传后再拉一次，防止两台设备同时同步时漏掉对方刚传的变更
```

### 为什么不全量同步？

全量同步每次都要遍历所有文件、对比哈希、传输全部内容，在文件数量大时非常慢。增量同步只传输发生变化的部分，速度快、流量小。

---

## 二、增量机制详解

### 时钟系统

每台设备维护两个时钟：

| 时钟 | 说明 |
|------|------|
| **localClock** | 自己产生的变更序号，每次上传一条变更日志 +1 |
| **remoteClocks** | 记录已处理过的其他设备的最大 clock，按设备 ID 分别记录 |

### 日志过滤

拉取远端日志时，过滤条件为：

```ts
entry.deviceId !== this.settings.deviceId &&
entry.clock > this.stateManager.getRemoteClock(entry.deviceId)
```

即：**只拉取其他设备的、自己还没处理过的新日志**。已经处理过的不会重复拉取。

### 续传机制（v0.1.4 新增）

`fetchRemoteEvents` 采用分块处理 + 检查点持久化：

- 每 50 条日志为一组，组内 10 并发拉取 + 解密
- 每组完成后立即更新 `remoteClocks` 并调用 `stateManager.save()` 持久化
- 如果同步中途中断（网络断开、手动取消、超时），下次同步从上次检查点继续
- **成功的日志**：推进 `remoteClocks`，下次自动跳过
- **失败的日志**：不推进 `remoteClocks`，下次重试

## 三、文件变更检测

### 基线索引

插件通过 `LocalIndex` 维护一份本地文件基线（文件路径 → hash + mtime）。每次同步时，对比当前 Vault 实际文件与基线：

| 情况 | 判定 | 动作 |
|------|------|------|
| 基线里没有，现在有 | **新增（create）** | 上传文件内容 |
| 基线里有，现在也有，但 hash 变了 | **修改（modify）** | 上传新内容 |
| 基线里有，现在没了 | **删除（delete）** | 上传删除日志 |

### 同步规则（SyncRules）

可以通过配置排除特定路径（如 `.obsidian/` 配置目录）。被排除的文件**不参与上传也不参与下载**。

---

## 四、删除同步

**删除操作会完整同步到其他设备。**

| 场景 | 行为 |
|------|------|
| A 删除文件 `xxx.md` | A 检测到基线有但实际已删除，上传一条 `{type: 'delete', path: 'xxx.md'}` 日志到 S3 |
| B 同步时拉到这条日志 | B 在本地执行 `deleteLocalFile('xxx.md')`，文件被删除 |

删除同步是**单向传递**的：A 删除 → B 同步时删除。反过来 B 同步时不会因为自己没有这个文件而触发删除（B 的基线里没有这个文件，不会产生删除事件）。

---

## 五、冲突处理

当两台设备几乎同时修改了同一个文件：

| 场景 | 行为 |
|------|------|
| A 和 B 都修改了同一文件 | **不覆盖**，后同步的一方检测到冲突，创建冲突副本 `xxx (冲突副本).md` |
| A 修改、B 删除同一文件 | 后同步的一方按自己的操作执行，另一方的操作通过冲突副本保留 |

冲突副本的命名规则：原文件名 + ` (冲突副本)` + 原扩展名。用户需要手动检查并决定保留哪个版本。

---

## 六、加密机制

所有上传到 S3 的内容都经过加密：

```
同步密码 → PBKDF2(password, salt=repoId) → AES-GCM 256 位密钥
```

- 文件内容：AES-GCM 加密后上传
- 变更日志：JSON 序列化后加密上传
- **密码必须一致**：多台设备必须使用相同的同步密码，否则无法解密对方的日志和文件

### 密码不一致的后果

如果 A 和 B 的同步密码不同：
- B 拉到 A 上传的日志后，解密会抛出 `OperationError`
- v0.1.4 起，单条日志解密失败不会中断整批同步，该日志被跳过
- 但对应文件无法同步，需要统一密码后重新触发变更

## 七、并发与容错（v0.1.4）

### 容错模式

`fetchRemoteEvents` 和 `uploadChangesConcurrent` 均采用逐条容错模式：

- 单条日志/文件失败不中断整批
- 失败的条目记录到控制台 `[同步管理器] 读取远端日志失败 xxx`
- 成功的条目继续处理

### 超时策略

| 层级 | 超时时间 | 说明 |
|------|---------|------|
| 单条 HTTP 请求 | 30 秒 | `ObsidianHttpHandler.requestTimeoutMs` |
| 单条 entry 队列超时 | 45 秒 | `ConcurrentQueue.timeout` |
| `fetchRemoteEvents` 阶段 | **不限时** | 依赖每条 entry 的 45s 超时兜底 |
| 其他阶段（上传等） | 180 秒 | `stageTimeoutMs` 默认值 |

### AbortSignal

`ObsidianHttpHandler` 支持 `AbortSignal`，阶段超时或手动取消同步时，底层 HTTP 请求会被真正终止，避免资源泄漏。

## 八、同步流程图

```
用户点击「立即同步」
        │
        ▼
┌─ 1. 扫描本地文件 ──────────────────────┐
│  对比基线索引，检测 create/modify/delete  │
└────────────────────────────────────────┘
        │
        ▼
┌─ 2. 读取远端日志 ──────────────────────┐
│  列出 S3 上的日志文件                     │
│  过滤：其他设备 + clock > remoteClocks    │
│  分块下载 + 解密（50条/块，10并发）        │
│  每块完成后持久化检查点                    │
└────────────────────────────────────────┘
        │
        ▼
┌─ 3. 应用远端变更 ──────────────────────┐
│  按时间排序，逐条应用                     │
│  create/modify → 下载文件内容到本地       │
│  delete → 删除本地文件                   │
│  冲突 → 创建冲突副本                     │
└────────────────────────────────────────┘
        │
        ▼
┌─ 4. 上传本地变更 ──────────────────────┐
│  逐条加密上传文件内容到 S3                │
│  逐条上传变更日志（localClock 递增）      │
│  更新本地基线索引                        │
└────────────────────────────────────────┘
        │
        ▼
┌─ 5. 追赶拉取 ─────────────────────────┐
│  再次拉取远端日志                        │
│  处理其他设备在本次同步期间上传的新变更     │
└────────────────────────────────────────┘
        │
        ▼
    同步完成
```

## 九、常见问题

### Q: 同步后另一台电脑没有收到删除？

确认两点：
1. 删除操作那台设备执行了同步（删除日志已上传到 S3）
2. 接收方执行了同步（拉到了删除日志并执行了本地删除）

### Q: 同步卡在「读取远端日志」怎么办？

v0.1.4 已修复此问题。如果仍出现：
- 打开控制台（`Ctrl+Shift+I`）查看具体错误
- 检查同步密码是否一致
- 检查网络连接是否正常
- v0.1.4 支持续传，再次点击同步会从上次检查点继续

### Q: 文件被修改了很多次，会传输很多次吗？

不会。每次同步只检测当前状态与基线的差异，只传最终状态。中间的修改历史不会产生多条日志。

### Q: 两台设备同时同步会冲突吗？

可能会。后同步的一方会检测到冲突并创建冲突副本。建议避免两台设备同时点击同步。
